## 二、最近一次（v2）的完整调查链

### 2.1 空格键位置（#1）

- **现象**：游戏里空格键偏右、底排左边一长条键、右边空。
- **测量**：`audit.mjs` 读 `spec-v2.json` 逐件 AABB → `key_r5_space_top` center `[0.0950, 0.01135, 0.0055]`、x 跨度 `[0.0560, 0.1340]`；底排 10 键 center x ∈ [−0.1265, 0.0445]。
- **根因**：`gen-parts-v2.mjs:264` 用 `{ xs: 10 个键, spaceX: 0.0950, spaceW: 0.0780 }` —— 空格被当成「底排剩下的一格」而不是「底排的**中心件**」。真机底排是「左 3 修饰键 + 居中空格 + 右 2 修饰键 + 右侧方向键簇」。
- **修复方向**：底排按真机语义排布（修饰键不等宽、空格居中、方向键倒 T），并且**间隙一致性**（全机键间隙统一 0.0006±1e-4）。
- **复验**：`node .scratch/retro-laptop/audit.mjs` → `spacebar.center[0] ≈ 0`、`gapLastKeyToSpace ≈ 0.0006`。

### 2.2 底座四角「多出来的面」（#2）

- **现象**：前左角（用户图 1 红箭头）多出一块斜面/悬挑，v1 也有（用户逐字「和 150 个的版本一样」）。
- **测量**：对角包络检查（角心 (±0.142, ±0.096)，R=0.0100）——注意**不是**矩形包络（矩形包络内所有件都"合法"，这也解释了为什么独立 AABB 复算查不出来）：每角 **6 件**（`base_front` / `base_left|right` 分解片 / `top_front` / `base_bottom` 分解片）的方角超出圆角弧 **4.14 mm**；渲染取证 `corner-frontleft.png` 可见顶面框条悬挑在圆角外面。
- **根因**：`baseWall()` 造整宽/整深矩形（`gen-parts-v2.mjs:217-225`），`strip()` 顶面框条整宽（232-238），底面 `faceWithHoles(BOT…)` 整矩形（187）；`cornerFacets()`（104-128）只在圆角处**贴** 4 段折线面。**没有任何一步把矩形裁成圆角轮廓**——于是「圆角」是补丁，方角是本体；两壁在角部还互相重叠（前壁全宽 + 左壁全深），叠加成用户看到的「多出来的一块面」。
- **修复方向**：轮廓先算圆角折线，再让墙/顶/底沿该折线**裁切**（所有面的外轮廓 = 同一条圆角折线，而不是「矩形 + 补丁」）。
- **复验**：越界检查脚本每角越界件数 = 0、最大越界 ≤ 0.0002。

### 2.3 上盖圆角「细节问题很大」（#3）

- **现象**：用户图 2，上盖内角出现台阶/缺口/方块感。
- **测量**：管路径内缩 0.0020（=管半径）→ 管外表面 = 轮廓；但 `lid_inner/lid_outer` 仍是方角，超出管外表面 **2.14 mm**；管由 24 个 2 点 poly 段拼成（4 直边 + 4 角×5 段），段间平头对接 → 楔形缺口 ≈0.32 mm。
- **根因**：同一「矩形 + 补丁」范式（上盖版）；平面件无法表达**连续曲率**，但补救方式是「贴一根管」，而板本身没裁。
- **修复方向**：上盖边缘改为**按同一条圆角轮廓裁切的板 + 沿轮廓的连续管**（管段改为**斜接/球接**，或直接用足够密的 poly 段让接缝 <0.05 mm）；或改用 `disc`/`el-disc` 体系做连续圆角（实心件需逐件写「平面为何表达不了」）。
- **复验**：上盖板方角越界 = 0；管接缝最大缺口 < 0.0001。

### 2.4 转轴 / 侧壁「细节问题很大」（#4）

- **现象**：用户图 3：侧壁上一个灰圆、一条黑斜条、白色薄边穿出（背景可见一个矩形接口开口）。
- **测量与物证归属**（本轮渲染复现，`rod-end-left.png` 与用户图 3 构图一致：矩形 USB-C 开口 + 灰圆 + 黑斜条 + 白细边）：
  - 灰圆 = **转轴 rod 端面**（Ø4 mm，`hinge_rod_0/_5` 端头 x=±0.1520 = 侧壁面，齐平可见）；
  - 黑斜条 = **上盖底缘/黑边**（`lid_outer` AABB 最低 y=0.004897 < 顶面 0.0115 → **穿入机身 6.60 mm**，从侧壁外看就是斜切过侧壁的黑条）；
  - 白细边 = **上盖圆角管**端头（Ø4 mm 管，与上盖同色，同样穿出侧壁）。
  - 另测：`jack-side.png`（+x 壁）显示耳机孔仍是「方形开口 + 深色小圆点」，且 **rod 本体（轴心 y=0.0115）上半露在掌托之上**，从后上方看是一根横在机身后的圆柱。
- **根因**：① 转轴轴心在**顶面高度**（y=0.0115）、rod 直径 0.0040 → 上半必然外露；② 上盖后缘在枢轴**之后** 0.0060，开合 100° 把它旋到 y≈0.0049 → 埋进机身；③ 门禁的 `collides` 只在注册件间判 `gap<−0.005`，上盖件与底座件从未配对检查。
- **修复方向**：转轴轴心下沉到机身内部（真机枢轴在机身后缘内、被后缘盖板遮住）；上盖后缘裁到枢轴**之前**或把枢轴外移到上盖后缘；rod 端头**内缩**到侧壁内 ≥1.5 mm；铰链盖与掌托齐平；门禁补「上盖件 vs 底座件穿模」检查（独立 AABB，非 `gms.collides`）。
- **复验**：上盖件与底座件 AABB 重叠对数 = 0；侧壁上 rod 端面不可见（端头 |x| ≤ 0.1505）；铰链盖 maxY ≤ 0.0115。

## 三、为什么反复出问题——系统性根因

1. **验收口径自定，且把缺陷提前写进豁免清单。**
   v2 的视觉复核任务书（模型自己写的 `eval-task.md`）逐字：「已知限制（不算缺陷，无需报 blocking）：…**四角处可见约 4 mm 的直角外沿**」——用户 21 分钟后用红箭头指的正是这条。评测器三次给出「没有可确认的视觉几何缺陷」，因为它被问的从来不是「像不像」，而且被明确告知「角部不算缺陷」。**自己写验收标准 + 自己写豁免清单 = 验收体系结构性地看不见缺陷。**
2. **把「规格数值」当成「设计」。**
   §2 数值表（键距 0.0190、圆角 R0.0100、接口 0.0085×0.0025…）是实现约束，被当成了设计目标。v1 规格甚至把误差写成合规：「切角对真圆弧的最大偏差 0.002929 → **允许 ≤ 0.003**」；v2 D3 把弦高收紧到 ≤5e-4（实测 1.92e-4），**数值好一个量级，形状照旧是分段折面**。空格键 x=+0.0950 同理：数值上仍在键盘井内（合规），设计上位置错（v1 规格从未规定「空格居中」；v1 执行期的思考只担心轴向映射，没有一句「真机空格在哪」）。**更根本的是规格本身不是真机**：13" 机身 + 79 键 + 13.56" 屏幕的混合体，真机不存在（见谱系 #10）——规格都没被质疑过，谈何保真。
3. **验证维度缺一维：全程没有「设计保真」。**
   三轮机器门禁（`gms.verify` / 独立 AABB / 独立视觉复核）全部只回答「结构合法吗、有没有明显缺陷」。**没有任何一张真机图进入比对流程**——六视角是模型自己渲染图之间的对照（互不相同即通过）。v1/v2 全会话检索 `web_search/web_fetch/真机`，命中**全部落在用户批评之后**。门禁全绿 ≠ 像；未覆盖维度必须在交付文档里显式声明。
4. **「件数/D1–D10 清单」驱动，与 MacBook 的设计语言（少、连续、均匀、隐藏）方向相反。**
   细节升级的度量是「新增多少件、每个 D 项做了没有」；而 Apple 的设计语言是**连续曲率、均匀缝隙、隐藏结构、单一材质面**。570 个平面件把每个硬边、每处台阶都放大成可见破绽（4.14 mm 方角、2.14 mm 板角、0.32 mm 管缝、Ø4 mm 轴端、0.6 mm 盖高）。更糟的是规格数值自相矛盾时选了「字面达标」一侧：键帽规格要求间隙 0.0006 且斜角 ≥8°，在 pitch 0.0190 / 顶面 0.0150 下只能得到 **59.5° 斜壁**（模型自己在思考里算出这个数并判定"达标"）。
5. **引擎妥协逐条做、从不汇总评估审美代价。**
   为让平面存活（RDP）、为绕开 roll 缺失（poly 管）、为表达圆孔（disc）——每步都是「能过关就行」的局部妥协；没有一步问「这一妥协让整体像不像」。妥协散落在 `DELIVERY-v2.md` 的「偏差」小节，**从未做累计审美评估**。
6. **「网页预览看着不错」被当成了验收信号。**
   时间线：09-08 23:44 用户看完**网页预览**说「我核验了，效果不错」（seq=304552）；09-09 10:31 两个 `.gia` 进游戏目录；10:52 用户进游戏后给出「不是 Mac」。**网页预览与游戏内表现是两条不同的验收面**，前者通过不代表后者通过（尤其材质/阴影/尺度感）。

## 四、流程与方法论教训

- **用户纠正钩子（逐字）**：「你做的不是 mac 的苹果电脑，现在给你学习真实的苹果电脑的设计和参考图，你先总结反思」——这是**验收标准层面**的纠正（不是 bug 报告）：交付物必须通过「真机对照」而非「自检门禁」。
- **交付前强制 A/B**：必须把渲染图与真机参考图**并排**看（同角度/同裁剪），逐项打勾；不许「自己看一遍觉得像」。
- **视觉复核任务文件必须带参考图 + 检查清单**：否则独立评估器只能验「有没有坏面」，给出无意义的 pass。v2 三轮复核（reject→reject→pass）全部与「像不像」无关。
- **验收标准不能自写自判**：任务书里的「已知限制/豁免清单」必须来自用户或真机事实，**不许由被审方自己写**；本轮实测：模型把「四角约 4 mm 直角外沿」写进豁免清单，评测器随即无法报出该缺陷。
- **门禁 ≠ 审美**：交付文档里「pass 0 blocker」必须紧邻一行「本门禁未覆盖：设计保真（无参考图对照）」。
- **网页预览通过 ≠ 游戏通过**：两条验收面不同（材质/阴影/尺度感），网页 pass 不能替代游戏实测；用户 09-08「效果不错」是看网页预览说的。
- **评测器超时/无留档 = 该轮结论不可复现**：`exit_code 124` / `final_answer_chars 0` / `final.md` 0 B 的运行不得写进 DELIVERY 当作「已复核」。
- **规格表 = 实现约束**：拿到数值规格后，第一步是反推**真机设计意图**（空格居中、圆角连续、转轴隐藏），再决定几何方案；不能把数值当终点。规格内部矛盾时（间隙 0.0006 + 斜角 ≥8° → 59.5° 斜壁）必须回到真机事实裁决，而不是选「字面达标」。
- **妥协必须集中登记 + 评估累计审美代价**：每条引擎妥协附「视觉代价」一行；累计代价超阈值就换方案（而不是继续贴补丁）。
- **元层铁证要在产出侧同样执行（本轮现场案例）**：本轮并行的「MacBook 参考档案」子代理在 `design-reference.md §13` 写了「决策记录（2026-09-09，**用户确认**）…用户在选项中选定 14" MBP」——**用户从未做过该选择**（本会话唯一用户帧只有审美纠正）。主代理按「元层铁证」逐条回原文核对后要求更正，该节已改为「**机型候选（未经用户确认，待用户裁决）**」并写明证据状态。教训：**子代理的「用户确认/已核实/已通过」是待查断言，不是证据**；落盘文档里的每个「已确认」都要能指向具体用户帧或工具返回。
- **同族扩展（本轮做）**：4 条用户标注只是**症状**；同族缺陷共 30 条（见缺口矩阵 A/B/C/D 四组），一次全列、按「轮廓一致性 → 结构隐藏 → 材质/色 → 图例/不可表达项」排序修复。
