# 演示视频 v2（2560×1440 · 离线逐帧）— 交付报告

> 2026-09-09 · 用户反馈三项（音乐嗡嗡声 / 片尾时长 + 致谢 / 提高分辨率）的落地记录。
> 产物：`delivery/demo-video/macbook-demo.mp4`（2560×1440 · 149.3 s · 77.2 MB · H.264 CRF18 + AAC 48k）
> 复现：`node scripts/max/demo-offline.mjs --out delivery/demo-video/macbook-demo.mp4 --w 2560 --h 1440 --fps 30 --q 0.92 --rtscale 2 --crf 18`

## 0. 用户反馈原文（验收口径）

1. 「整个音乐，出现的嗡嗡翁的声音，可以减弱，但是音效还可以，尤其是前面部分，后面部分的音效我没有那么满意。」
2. 「后面部分的整体时间可以缩短一点点，最后加上礼貌的感谢观看的观众，能看到最后是很有耐心的观众啦。」
3. 「是不是还可以提高一点画质，升级渲染的分辨率。？」
4. 中途提示（研究方转达）：「试试 2560x1440 画质，gpu 渲染，调优一下。」

## 1. 先量瓶颈：实时录制的帧率天花板 = 输出像素数

同一台机器、同一页面、MediaRecorder 实测（每档 13–18 s，`scripts/max/demo-record.mjs`）：

| 输出分辨率 | 内部 RT 倍率 | 帧率 | 每帧成本 |
|---|---|---|---|
| 1280×720 | rtScale 2（2560×1440 RT） | 30 fps（卡在 `captureStream(30)`） | — |
| 1600×900 | rtScale 1 | 42–49 fps | ~20–24 ms |
| 1920×1080 | rtScale 1 | 29–33 fps | ~30–34 ms |
| 2560×1440 | rtScale 1 | **16–20 fps** | ~50–62 ms |
| 2560×1440 | rtScale 2 | 11–13 fps | ~80 ms |

换算下来 **~15 ms / 百万像素**，与编码器、画质档、`--nocopy`（跳过 2D 合成拷贝）都无关：

- VP8 / VP9 / MP4(H.264, MediaRecorder) / WebCodecs(avc1.640033) 四路都试过：1440p 分别是 17–20 / 10 / 17–19 / 10 fps。
- 去掉合成画布拷贝（直接抓 WebGL 画布）：1440p 只从 16 fps 升到 17–20 fps。
- 页面自身 GPU 成本实测：1440p 渲染 **1.2 ms**（rtScale 1）、**4.3 ms**（rtScale 2）、4K rtScale 1 **6.5 ms**——GPU 完全不是瓶颈。
- 瓶颈在浏览器主线程的**抓帧 + 编码**（`toDataURL` / `captureStream` 读回）。

结论：**实时路线在 1440p 上不可能到 30 fps**，与「调优」无关。采纳用户提示「视频不必实时」，
改**离线逐帧**。

## 2. 离线逐帧管线（v2）

```
页面内：drawFrame(t) → cv.toDataURL('image/jpeg', 0.92)  ─┐
         t += 1/30（绝对时间步进，帧率与机器性能解耦）      │  CDP 批量取回（4 帧/次）
                                                          ▼
本进程：ffmpeg -f image2pipe -vcodec mjpeg -framerate 30 -i pipe:0
        -c:v libx264 -preset medium -crf 18 -pix_fmt yuv420p -r 30
        -i offline-audio.wav -c:a aac -b:a 192k -movflags +faststart
```

- 新文件 `scripts/max/demo-offline.mjs`（Node 侧驱动）；`scripts/max/demo-inject.js` 新增离线分支
  （`window.__offline = {fps, q}` → `__offNext(n)` / `__offShot(t)` / `__offAudio()` / `__offTimeline`），
  并把逐帧绘制抽成 `drawFrame(t)`，实时录制与离线渲染**共用同一条时间轴与同一套绘制代码**。
- **音轨也离线**：`OfflineAudioContext(2, 48 kHz)` 上跑同一套 `buildAudio()` 排程 → 16-bit WAV → AAC。
  实时录音轨受性能影响的隐患（丢帧/卡顿）一并消除。
- **分辨率相关的一切按 K = H/720 等比缩放**：字号、行距、边距、渐变高度全部乘 K，
  1440p 下字幕观感与 720p 完全一致（否则文字会缩小 33%）。
- 内部仍开 **rtScale 2**（5120×2880 渲染 → 1440p 降采样）：GPU 只多花 3 ms/帧，得到干净的边缘。

**实测成本**：4479 帧 / 20.4 分钟 = **3.66 帧/秒**（瓶颈是浏览器里的 JPEG 编码，约 250 KB/帧），
整段管道吞吐 984 MB JPEG → 77.2 MB MP4。

## 3. 音轨：嗡嗡声的量化来源与修法

频谱对比（Welch 平均，20 Hz–16 kHz 归一，v1 成片 vs v2 成片）：

| 频段 | v1 | v2 | 变化 |
|---|---|---|---|
| **20–60 Hz** | −21.2 dB | **−35.1 dB** | **−13.9 dB（嗡嗡声）** |
| 60–120 Hz | −5.4 dB | −6.3 dB | −0.9 dB |
| 120–250 Hz | −3.8 dB | −3.2 dB | +0.6 dB |
| 250–800 Hz | −5.7 dB | −5.8 dB | 持平 |
| 800–2500 Hz | −17.8 dB | −17.1 dB | +0.7 dB |

峰值 0.747 → 0.683（多出 0.7 dB 余量），RMS 0.0604 → 0.0682（整体略响）。

改动（`scripts/max/demo-inject.js`）：
- **删掉贯穿全片的 55 Hz sine drone**（`tone(a0, 55, 67, 0.014, 'sine')`）——嗡嗡声的第一来源。
- 房间底噪：`noise(a0, 67, 240, …, 0.010, 'lowpass')` → `noise(a0, TOTAL, 620, …, 0.0030, 'lowpass')`
  （低通 240→620 Hz，增益 −10 dB，且铺满全片）。
- `padTone` 串一级 **highpass 105 Hz / Q 0.7**：把 F2/G2 根音（87/98 Hz）的基频压下去，和弦仍完整。
- **片尾音效重做**（用户对后半段不满意）：旧的「翻页」噪声（1.5 kHz 带通 50 ms）换成
  **两音上行玻璃铃**（880–1318 Hz 音阶循环，1.9 s 衰减 + 一丝 4.2 kHz 空气感），
  每 3 张卡加一次极轻的 pad 呼吸（220/329.63 Hz，5 s 渐入渐出）。
- **谢幕卡专属音**：523.25 → 659.25 → 783.99 三音上行 + 174.61/261.63 Hz 暖垫（是可闻乐音，不是 drone）。

## 6. 踩过的坑（本轮新增）

1. **`fr.result.split(',')[1]` 会切错**：mime 里的 codecs 参数自带逗号（`avc1.42E01E,mp4a.40.2`），
   实测写出 9 字节垃圾文件 → 改成按 `';base64,'` 定位。
2. **ffmpeg 输出选项必须排在所有输入之后**：`-r 30 -fps_mode cfr` 放在第二个 `-i` 之前，
   ffmpeg 会当成 WAV 的输入选项直接报错退出 → 管道 EPIPE。
3. **每个 bash 调用是独立 PID 命名空间**（`bwrap --unshare-pid`）：`ps` 看不到别的调用起的进程，
   「进程没了」的判断不能靠 `ps`，要看输出文件是否还在长。
4. **后台标签的 rAF 会被节流到 0**：性能测量脚本必须先 `Page.bringToFront`，
   否则量到的是「0 帧」而不是真实帧率。
5. **1440p 下所有画布文字必须乘 K = H/720**：否则字幕/水印/寄语卡文字会缩到 2/3 观感尺寸。
6. 实时路线的错误方向（记录）：先怀疑 GPU（错，GPU 6 ms/帧）、再怀疑编码器（错，换编码器没变）、
   再怀疑合成拷贝（只占 2 ms）——**只有按像素数线性外推才解释得通**。

## 7. 已知缺口（不藏）

- 扬声器开孔未建模；侧壁散热槽未建模；屏幕内容是用户提供的桌面截图（跨视角共用同一张）。
- 离线管线的 JPEG 中间层（q0.92，~250 KB/帧）是唯一的有损环节；若日后要无损，
  可换 `toBlob('image/png')` + 磁盘序列（代价：约 2.5 GB 中间文件、速度更慢）。
- 20 分钟渲染时间与机器性能解耦，但**帧率恒定 30 fps 是硬保证**（离线步进，不会丢帧）。
